# Inventory transfer recovery

The DM Toolkit bank ledgers view includes pending inventory operations recorded by the transaction journal: personal bank, party treasury, storehouse, character-sheet purchases, and character-to-character transfers. Actor UUIDs identify token inventories separately from their world actors.

When a pending transfer appears, inspect its journal snapshot and click **Retry recovery**. The result is reported honestly:

- **Committed** means the live state matches the transfer's after snapshot and the journal was cleared.
- **Restored** means the live state was returned to the transfer's before snapshot and the journal was cleared.
- A recovery failure remains pending and requires manual reconciliation using the displayed snapshots. The system refuses to auto-overwrite unknown drift.

Bank, treasury, and storehouse edits now run through one active-GM queue, including personal accounts, catalog grants, and direct DM edits. An active GM must be connected. Browser Web Locks elect one executor across GM tabs in the same browser profile; browser authority requires Web Locks in a secure context. Keep the active GM signed in through one browser profile/device. Separate profiles/devices do not share browser locks. Recovery is performed from the authority GM tab. Planning reads the GM's current documents and checks the requesting user's ownership; shared accounts also require party membership.

Each request has a stable operation ID. Pending requests share that ID for double clicks, retries, delayed acknowledgments, and reconnects in the same browser tab. A timeout means the outcome is unknown: retry the same action. Completed receipts return their recorded result without moving value again. Reusing an ID with a different payload or requester is rejected. After acknowledgment, a deliberate new action receives a fresh ID. Integrations can supply an explicit operation ID when replaying a previously acknowledged request.

The Bank Ledgers view also lists **Pending authority operations**. These block new bank/store edits globally. Use their **Retry recovery** action: it reconciles the durable transaction snapshot and retains a completed receipt, including cancelled operations, so replay cannot repeat them. An operation interrupted before preparing a transaction is cancelled without moving goods. The existing actor-journal recovery button also routes authority-owned records through this queue and finalizes their receipt.

During GM handover, the former authority stops at the next write or compensation boundary. The new GM honors persisted receipts and recovers interrupted transactions before accepting new edits. Foundry does not offer server-side compare-and-swap fencing: a write already submitted may finish after authority changes. Unknown drift remains blocked for manual reconciliation; live multi-client handover acceptance is still required. External Foundry item/flag edits and character-sheet purchase/gift queues are outside this bank/store authority and can produce unknown drift.

Receipts are intentionally retained without automatic expiry. Do not delete them to unblock operations: doing so would allow old requests to duplicate value. Receipt retention and backup sizing should be evaluated before long-running production use.

If recovery refuses because live data matches neither snapshot, back up the world before making corrections. Compare both affected records with the displayed before/after snapshots and account for any later legitimate changes. A GM can correct inventory using Foundry's item editor and, when necessary, correct actor flags/world settings using Foundry's document tools. Bring both endpoints to a consistent recorded before state or after state, then click **Retry recovery** again. The journal is cleared only after that state is confirmed. Do not delete a pending journal to bypass the check or blindly replay the original transfer.

The journal also covers interrupted operations after reconnecting or restarting Foundry. A retained record whose endpoints already match the after state is finalized without moving goods again. A record whose endpoints match the before state is cleared as restored. Conflicting operations on either actor, bank/storehouse operations, and manual account edits remain blocked while a related recovery is pending. If a recorded actor or token is unavailable, recovery stays pending rather than targeting a different actor with the same ID.

Character-sheet drops select quantity and validate placement on detached inventory copies. Player catalog acquisitions are purchases; catalog currency and treasure are loot; GM catalog grants are free; another actor's items are gifts or loot; same-actor drops are internal moves. Gifts, loot, and internal moves do not charge the recipient. Purchases commit payment and placement together. Closing the quantity dialog cancels without writing. A container or animal with contents must move as a complete stack; the transfer includes all descendants and remaps their parent links. When no valid storage or wearing position exists, choose another destination before acquiring the item.
